# Миграция EnDesign: MODX → Next.js + Payload CMS

**Этап 1 — Аудит и планирование.** Ниже — полная инвентаризация текущего сайта, обоснование
выбора нового стека и пошаговый план переноса. Код приложения на этом этапе не пишется.

## Контекст

Сайт студии дизайна **EnDesign** (endesign.firstweb.org.ua) работает на MODX Revolution 2.8.5-pl
(`C:\xampp\htdocs\endesign`, БД `endesign_firstweb`, префикс таблиц `ends_`). Задача — полностью
перенести сайт на современный стек (Node.js/TypeScript/Tailwind) с удобной админ-панелью,
позволяющей редактировать тексты, картинки и страницы без правки кода — по аналогии с тем, как
сейчас редактируется контент в MODX Manager.

**Обновление после старта Этапа 2:** на диске не было SQL-дампа, поэтому Этап 1 опирался на
частичное восстановление контента из кэш-файлов ModX. В начале Этапа 2 локальный MySQL (XAMPP)
был поднят и снят полный `mysqldump` (`migration/db/endesign_firstweb.sql`, 2.5 МБ, все 84
таблицы, без ошибок). Все данные ниже в разделе 1 уже уточнены по реальному дампу — они точны
и являются источником правды для схемы Payload и скрипта импорта.

Подтверждённые решения:
- Языки нового сайта: **uk (основной) + ru + en** (английский добавляется новым — потребует
  перевода части контента, которого сейчас нет на en).
- Хостинг: **VPS + PostgreSQL**, self-hosted, полный контроль (Docker).

### 1.4 TV-поля (72 штуки, точный список из `ends_site_tmplvars`) — критично для модели данных
Развитая система **повторяемых блоков**, три префикса под три типа страниц:
- `topcat_block_1..9_*` (тип `Верхняя категория`) — заголовок/текст/подзаголовок/список
  (список — тип `migx`, т.е. повторяемая под-таблица, обычно карточки/иконки)
- `childcat_block_1..9_*` (тип `Вложенная категория`/услуга) — те же паттерны + `gallery`,
  `icons`, `img`, `wtext` (текст на белом фоне)
- `prod_block_1,2,7,8,9` и `for_prod_block_3` (тип `Продукт`) — заголовок/текст/галерея/список
- SEO (на все типы): `seo_title`, `seo_keywords`, `seo_description`
- Шапка/главная: `header_img`, `header_text`, `title_2`, `subtitle_2`, `home_svg`, `client_img`,
  `which_business`
- Контакты: `cont_phone_1/2/3`, `cont_telega`, `cont_viber`, `cont_whats`, `cont_mail`
- Категория: `cat_text`, `cat_img`, `cat_price`, `gallery`, `list_2`
- Портфолио: `client_img_cat`

Не каждый блок заполнен на каждой странице (номера блоков 1–9 не идут подряд равномерно —
некоторые пропущены, что нормально для ModX: TV создавались по мере роста контента). Это
напрямую диктует архитектуру CMS: **Blocks-поле с переиспользуемыми типами блоков** (Title+Text,
Gallery, Icon List, Text+Image, Price) вместо жёстко заданных `block_1..9` полей — редактор
сможет добавлять/убирать/переставлять блоки в любом порядке, без привязки к номеру.

### 1.4.1 Архитектура мультиязычности (уточнено по дампу — важно для импорта!)
В базе нет отдельных "контекстов" per-язык — все страницы физически хранятся один раз в
`ends_site_content` (это и есть украинский, язык по умолчанию, `culture_key='uk'`). Плагин
**Polylang** хранит переводы в отдельной таблице `ends_polylang_content` (52 строки) как
**оверрайд по `content_id` + `culture_key='ru'`**: `pagetitle`, `seotitle`, `keywords`,
`longtitle`, `menutitle`, `introtext`, `description`, `content`. Настроено **только 2 языка**:
`uk` (`ends_polylang_language` id=1, домен без префикса) и `ru` (id=2, префикс `/ru/`) —
**английского нет вовсе**, TV-значения (картинки, telefony, галереи) при этом НЕ дублируются
по языкам — общие для uk/ru. Для импорта: читаем базовую (uk) строку из `ends_site_content` +
TV-значения из `ends_site_tmplvar_contentvalues`, затем оверрайдим текстовые поля из
`ends_polylang_content` для ru-локали; en-локаль в Payload создаём как новый пустой/переводимый
слой поверх uk-структуры (черновой перевод + ручная проверка, как и планировалось).

### 1.5 Чанки и сниппеты (для справки, не переносятся как код — эквивалент в React/Payload)
48 чанков — в основном частичные шаблоны блоков (`topcat_block_2_list`, `childcat_block_4_icons`
и т.д. — рендерят `migx`-списки в HTML) и структурные части (`header`, `footer`, `top_menu`,
`breadcrumbs`, `parent.menu`/`children.menu` — автогенерация меню из дерева страниц). В новом
стеке всё это — обычные React-компоненты, работающие с типизированными данными из Payload, а не
со строковым HTML — сравнивать 1-в-1 не нужно.

45 сниппетов — почти все являются кодом установленных плагинов (pdotools, Polylang, MIGX,
phpthumbof/pthumb, svgSanitize) и не относятся к уникальной логике сайта. Единственный
**кастомный** сниппет — **`EnDesign_API`** (нет описания в БД) — его содержимое стоит открыть и
прочитать перед импортом: может скрывать интеграцию (форма заявки → CRM/Telegram/почта,
калькулятор цены и т.п.), которую нужно будет переосмыслить как API-роут в Next.js.

## 2. Выбор стека — обоснование

### 2.1 Фронтенд: Next.js 15 (App Router) + TypeScript + Tailwind CSS v4 + shadcn/ui + Framer Motion
- **Next.js App Router** — серверные компоненты для быстрой первой загрузки (важно для
  портфолио-сайта с тяжёлыми изображениями), встроенная маршрутизация `[locale]` идеально
  ложится на задачу uk/ru/en, ISR/on-demand revalidation — правки в CMS появляются на сайте
  без пересборки.
- **Tailwind CSS v4** — быстрая, современная типографика и адаптивность, легко создать
  выразительный дизайн для портфолио.
- **shadcn/ui** — копируемые в проект компоненты (кнопки, формы, диалоги), а не библиотека-
  зависимость — полный контроль над стилями для нестандартного дизайна студии.
- **Framer Motion** — плавные анимации появления блоков/галерей, hero-видео, переходы между
  страницами.
- Next.js вместо Astro: сайту нужна CMS-админка с live-preview и превью черновиков — Next.js
  и Payload разработаны для совместной работы в одном репозитории (App Router отдаёт и
  публичный сайт, и `/admin`), что снижает сложность инфраструктуры.

### 2.2 Backend/CMS: Payload CMS 3 (self-hosted, встроен в тот же Next.js проект)

| Критерий | Payload CMS 3 | Strapi | Decap CMS (git-based) |
|---|---|---|---|
| Стек | TypeScript-native, живёт **внутри** Next.js app (`/admin` route) | Отдельный Node.js сервис, своя БД/деплой | Статичный, коммитит правки в git |
| Повторяемые блоки (topcat_block_N) | **Blocks field** — ровно то, что нужно: редактор добавляет/убирает/переставляет блоки нужных типов | Dynamic Zones, менее гибкая типизация в TS | Нет нормальной поддержки — только плоские markdown-поля |
| Медиа/картинки | Встроенная Upload-коллекция, авто-ресайз, фокальная точка кадрирования | Есть Media library | Через git LFS/папку — неудобно для нетехнического клиента |
| i18n (uk/ru/en) | Встроенная локализация полей «из коробки» | Плагин i18n, менее интегрирован | Нет нормальной мультиязычности |
| Простота для нетехнического пользователя (клиент студии) | Админка похожа на привычный CMS-интерфейс (как MODX Manager) | Похоже | Требует понимания git/OAuth — «эффект второй системы» |
| Инфраструктура | 1 приложение (Next.js+Payload) + 1 Postgres | 2 приложения, 2 деплоя, 2 БД | Без БД, но и без полноценного администрирования медиа |

**Вывод:** Payload CMS 3 — блочная модель 1-в-1 повторяет существующую структуру TV-полей ModX,
родной TypeScript, единый деплой с фронтендом на VPS, полноценная админка «из коробки» не хуже
MODX Manager по удобству для клиента.

### 2.3 База данных: PostgreSQL
Payload Postgres adapter, деплой на том же VPS через Docker Compose (`app` + `postgres`).
Для поиска по-русски/украински при необходимости — `unaccent`/`pg_trgm`.

### 2.4 Инфраструктура
- **Docker Compose** на VPS: контейнеры `web` (Next.js+Payload, один процесс), `postgres`,
  `nginx` (reverse proxy + TLS через Let's Encrypt/certbot).
- Медиафайлы: локальный volume на VPS (с бэкапом), с опцией переключить на S3-совместимое
  хранилище (Cloudflare R2) позже одной строкой конфига.
- CI: git push → build → деплой (GitHub Actions или ручной скрипт на VPS).

## 3. План переноса — пошагово (детальные тикеты — уже в Этапе 2)

1. **Извлечение данных** — поднять локальный MySQL (XAMPP), `mysqldump endesign_firstweb`,
   распарсить `ends_site_content`, `ends_site_tmplvar_contentvalues`, `ends_site_templates`,
   `ends_polylang_*` → получить полный, точный список страниц на uk/ru со всеми TV-значениями.
2. **Проектирование схемы Payload** — коллекции: `Pages` (localized), `Services`, `Categories`,
   `CaseStudies` (портфолио), `Media`, `SiteSettings` (глобальные — контакты, соцсети, SEO
   defaults). Блочные поля: `Hero`, `TitleText`, `Gallery`, `IconList`, `TextWithImage`,
   `PriceBlock` — на основе паттерна `topcat_block_N`/`childcat_block_N`.
3. **Импорт контента** — скрипт-мигратор (Node.js), читающий распарсенные строки MySQL и
   создающий записи через Payload Local API — переносит uk+ru контент как есть; en — плейсхолдер
   под перевод.
4. **Перенос и оптимизация ассетов** — транслитерация кириллических имён файлов, загрузка в
   Payload Media (авто-генерация responsive размеров), замена ссылок в мигрированном контенте.
5. **Вёрстка публичной части** — компоненты по типам страниц (§1.3) на Tailwind+shadcn,
   рендер блоков через маппинг `blockType → React-компонент`, анимации Framer Motion,
   `[locale]` роутинг App Router.
6. **Админка** — Payload `/admin` из коробки, роли доступа (редактор студии — тексты/картинки,
   без доступа к коду), preview-режим черновиков.
7. **SEO и редиректы** — карта старых URL → новых (сохранить алиасы, где возможно, 301 для
   остальных), sitemap.xml, meta по seo_* TV.
8. **Тестирование и запуск** — визуальная сверка каждой страницы со старым сайтом, проверка
   форм (контакты), деплой на VPS, DNS-переключение.

## 4. Концепция дизайна
- Тёмный/светлый режим с акцентным ярким цветом бренда (взять из текущего лого/палитры).
- Крупная типографика для заголовков услуг, hero-секция с фоном/видео (`hero-loop.mp4`
  сохранить), скролл-анимации появления карточек услуг и кейсов портфолио.
- Портфолио — grid/masonry с hover-эффектами (заменяем текущий slick carousel на современный
  Embla/Framer carousel).
- Блочная страница услуги — секции чередуются (текст/картинка, галерея, список с иконками),
  без ощущения «шаблонности» за счёт вариативности блоков.
